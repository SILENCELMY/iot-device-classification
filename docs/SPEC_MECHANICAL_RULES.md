## 1. 实验登记（原协议 §19.1）

**规则**：每次实验**开工前**在 `docs/EXPERIMENT_REGISTRY.md` 登记一行，
字段为实验 ID / 日期 / commit / 配置 / 种子 / 输入路径 / 输出路径 / 结论 / 是否进正文。
跑完补「结论」。纯分析脚本改动也要**先提交再跑**，commit 列填 `git rev-parse HEAD`。

**为什么**：防止事后挑选。开工前登记使"跑了几次、报了哪次"可查。
2026-08-28 有过一次实例：E1-ARMS-VERIFY 首次登记的数字后被发现来自一个
`_splitter` 缺陷（多轮分组分支缺 `return`），修正后**方向与原记录相反**——
因为有登记行，这次修正是可追溯的公开更正，而不是静默改数。

**今天仍在用**：`C3-CONFIRM-UNSW16` 就是照这条做的预登记，
协议 §8/§9 的两次修正都在登记行留了痕。

## 2. 种子

**规则**：默认 `SEED = 42`；需要稳健性时用 42 与 43 两个种子**并报两个数与差**，
不允许只报好看的那个。

**为什么**：单种子的结论无法与"随机波动"区分。两种子并报是成本最低的下界检查。

**今天仍在用**：C3 确证两种子，差 0.0001；轻度验证两种子，差 0.0003。

---

## 3. `day_gate`：设备/天的入选门槛

**规则**：一个 (设备, 天) 进入任务，须满足该天该设备的窗口数达到门槛。
实现在 `results/unsw_iid_reference_20260902/run_unsw_iid_reference.py::day_gate`，
需要 `device / label / day / window_id` 四列。

**为什么**：跨天任务里，某些设备在某天只有个位数窗口。不设门槛会让类别在不同天之间
悄悄出现或消失，使"跨天下降"混入"类集变化"。门槛后取**各天交集**，类集才恒定。

**今天仍在用**：UNSW 45 对账本、C3 两臂、CIC 全部实验的类集都由它定。
C3 的类集 = 训练天 ∩ 选参天 ∩ 保留 16 天 的 `day_gate` 交集。

## 4. 特征族的导出规则

**规则**：按列名的**首个下划线段**分组；成员数 < 2 的并入 `singletons`。

**为什么**：族掩码是方法的候选空间。如果族由人手工划分，"掩掉哪一族有效"就
无法与"划分划得巧"区分。机械规则使族在**跨数据集之间可比**，也使结果可复现。

**今天仍在用**：自采 94 列 → 10 组；UNSW 62 列 → 7 组；本文 130 列 → **14 组**。
`cfg_strong.py` 里有一条断言 `assert "lenhist" in fams`，
就是在检查新加的 69 列确实按这条规则成了一族，而不是被打散。

## 5. OOF 模式：`random` vs `grouped`

**规则**：stacking 的元层训练数据，OOF 折划分有两种模式——
`random`（随机折）与 `grouped`（按轮次/环境分组）。**跨环境任务必须用 `grouped`**。

**为什么**：`random` 折让同一轮次的窗同时出现在训练和验证里，元层因此看到的是
"同环境"的基模型行为，与部署时"跨环境"的行为不一致，会低估崩溃。
实测：同一任务 `random` 下 macro 0.5455，`grouped` 下 **0.4907**，
崩溃**加深约 1.8 倍**（E1-ARMS-VERIFY，commit `6a3f678`）。

**今天仍在用**：stacking 崩溃 −0.0961 这个数依赖 `grouped`；
它是 C1 的第一处证据（新主线 §11.2）。

**⚠ 已知边界**：`loro_R2_R4_to_R3` 只有 2 个源轮次，`GroupKFold` 的 `n_splits`
退化为 2（每折单轮训练、另一轮验证），元特征噪声显著大于 5 折。
单轮/IID 任务无法按轮次分组，按时间块并**单独标注**。

## 6. 评价口径

**规则**：**窗口级 macro-F1 为主判据**，设备级只并报，不作判据。
逐类对的数与端到端的数**必须并报**。

**为什么**：设备级只有 192 块，已饱和，分辨不出差异。
而 macro-F1 会稀释——一个类对的彻底翻转在 29 类里只体现为 +0.0075；
只报端到端会得出"方法无效"的错误结论，只报逐对会被读作挑选有利类对。

**今天仍在用**：C3 结论同时报了「区上 +0.0417」与「端到端 +0.0080」。

## 7. 逐对度量的投影口径（2026-09-05 新增，非原协议）

**规则**：三个量必须分清，且**同时并报**：

| 问题 | 用哪个量 |
|---|---|
| 这对分不分得开 | **对内准确率**：概率**限制到 {i,j} 两列**后 argmax |
| 这对解没解 | 该对**自己的**错误量 / 错误占比 |
| 闸门的作业面 | **区上准确率**，且在位者与候选在**同一个区**上量 |
| 可分性上界 | 专用二分类器，且与被比较者**同一平滑/聚合口径** |

**为什么**：2026-09-05 一天内因投影口径不一致犯错**五次**，其中一次出在方法本身
（闸门在子集上记账、对超集施加，区上 +0.18 而端到端 −0.0085）。
详见新主线 §4 的三处修正。

**附加**：诊断用的模型必须是**部署用的模型**。
`pair_auc` 曾用 LR 诊断树的部署，逐类对差 0.15–0.86 且方向相反。

## 8. 承重脚本必须在仓库内（2026-09-06 新增，由一次真实失误产生）

**规则**：
1. 任何产出**进正文数字**的脚本，必须位于仓库内并**在实验开跑前提交**；
2. 协议须**钉住脚本的 commit 或 sha256**；
3. 实验产出目录须与该 commit 一同可追溯。

**为什么**：2026-09-06 外部审阅（fable）指出——C3 确证的脚本位于 `~/cic_probe/`，
**仓库外、无版本控制**。结果落盘 00:02–00:24，脚本被就地修改到 01:54（审计修正 8/9/1）。
**产出确证结果的那一版因此不复存在**，"确证测的就是代码做的事"这句话无法核对。
同一目录下 83 个脚本全是这个状态。

**已做的补救**：
- 全部脚本与运行日志纳入仓库根下的 `scripts_exploratory_20260906/`
  （**不是** `code/scripts/`：`.gitignore` 排除 `/code/`，第一次补救放进那里被静默忽略，
  见该目录 README；本条初稿也写错了路径，2026-09-06 由第二轮审阅更正）；
- as-run 版由三处明确补丁**逆转重建**为 `c3_confirm_ASRUN_reconstructed.py`，
  文件头写明"重建、非当时副本、未经逐位验证"；
- 本机 `research-results` 分支推送到服务器，预登记链的 commit 时间戳
  （协议 20:54 / 修正 21:19 / 23:27 / 结果 00:25）在服务器上可独立核对。

**这条补救不能替代规则**：重建的 provenance 清楚，但不等于当时保留。

## 9. 跨机器同步：累积型文件先比对再覆盖（2026-09-06 新增，由一次险些毁档的失误产生）

**规则**：
1. **区分两类文件**。
   - **快照型**（协议、主线、单次实验的 spec）：内容由一次写作决定，覆盖是安全的。
   - **累积型**（登记表、`MEMORY.md`、汇总文档、索引）：内容由**多次追加**积累，
     **覆盖 = 删除对方独有的历史**。
2. **累积型文件禁止 `scp` 整体覆盖**。跨机器同步时必须：
   ```
   先比对    diff <(远端版) <(本地版)   或  git show <远端分支>:<路径>
   再判断    哪一侧是"权威侧"（通常是历史更长、提交更多的那一侧）
   最后      只把自己【新增的那几行】追加到权威侧，不整体覆盖
   ```
3. **权威侧一旦确定就写进文档**。本项目：**登记表以服务器 `main` 为准**。
4. 两台机器历史分叉期间，**每次同步都要重新判断**，不能因为上次覆盖没出事就沿用。

**为什么**：2026-09-06 凌晨，为修复"预登记链在服务器上不存在"，
把本机 `docs/` 的五个文件 `scp` 到服务器，其中包含 `EXPERIMENT_REGISTRY.md`。
本机分支初始化自 **08-28 的 7 行快照**，此后 09-04/09-05 在服务器 `main` 上登记的
**28 个实验它一个都没有**：

```
                  登记行数   文件行数
服务器 main HEAD      35        98
被覆盖后的工作区       8        44
```

将丢失 `E1-FULL`、`G0-GRID`、`S1-DEEP-5SEED`、`P2-UNSW-PILOT`、
`UNSW-TWO-CHANNEL-ANCHOR/VALIDATE`、`PAIRWISE-OVERRIDE`、`OVERRIDE-183`、
`TRANSMITTER-PARTITION-VALIDATE` 等 28 个 ID，
连带 08-29 那条 **GroupKFold 折数的裁决记录**（§5 的 `n_splits` 退化边界即出自它）。

**由外部审阅在提交前指出，改动尚未 commit，`git checkout main -- <路径>` 救回。**
处置：还原 `main` 版，只追加 `C3-CONFIRM-UNSW16` 一行，35 → 36。

**这次不是判断失误，是机械操作失误**：两台机器分叉了一整天，我一直知道，
却在同步时没想到"本机版本可能落后"这一层。
**⇒ 靠记性不行，必须写成规则。**

**关联**：同一次审阅还指出第二处 —— 承重脚本被放进 `code/scripts/`，
而 `.gitignore` 第 8 行排除 `/code/`（服务器上 `code/` 是独立仓库），
**85 个文件被静默忽略**。补救见 `scripts_exploratory_20260906/README.md`。
⇒ **推论：`git add` 之后要核对 `git diff --cached --name-only` 里确实有你以为加进去的文件。**
