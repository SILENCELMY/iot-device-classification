# 方法规格：跨环境部署的配置推导程序（工作草案）

**日期**：2026-09-04
**性质**：**规格文档,不产生任何数字**。所有引用的数都来自已冻结协议的产物,逐条标出处。
**目的**：把散在四个 runner 里的五步串成一个可调用的方法,并写明它是什么、不是什么。

> **这不是一个新的分类器。**它是一个「给定特征集与模型栈,为跨环境部署推导配置」的程序,
> 附带一个无标签置信信号与一个明确的不开火条件。它**不产生新信息**,因此**不抬逐窗口天花板**。

---

## 1.1 可采性门：候选池的第一道门（**在验收门之前**）

用户 2026-09-04 提出的硬性限制：**重抽的特征必须是新环境容易拿到的，否则没有用。**
形式化为候选池的准入条件：

> 一个候选特征**可采** ⟺ 它能从「**声明的部署位置**上的被动抓包」算出，
> 且不需要解密密钥、不需要设备配合、不需要目标标签。

**必须先声明抓包位置，候选池随之确定。两种位置的可采池几乎不相交**：

| | 位置 A：802.11 monitor 模式（自采） | 位置 B：网关/交换机镜像（UNSW、CIC） |
|---|---|---|
| 802.11 帧头（`rssi`、速率、重传、`subtype`、duration、信道） | ✅ | ❌ |
| 帧长与时间统计 | ✅ | ✅ |
| 上下行方向（需 BSSID，帧头可得） | ✅ | ✅ |
| IP/TCP 头、端口、双向流 | ❌（WPA2 下已加密） | ✅ |
| DNS / TLS 元数据 / 应用层 | ❌ | ✅ |

**这道门解释了 `rssi` 为何无法外部复现**：它只在位置 A 可采，而 UNSW/CIC 都是位置 B。
**「干预效应量不可外部复现」与本限制是同一问题的两种说法。**

**立场（用户 2026-09-04 定，取代此前拟的「A/B 二选一」）：不择一。特征池是**声明的输入**，
不是论文的假设 —— 不同位置选取不同特征，本质要求是**提升各自环境下的识别准确率**。**

方法因此是**位置无关**的：它不声称一套通用特征集，只声称一个**在任何位置所能提供的池上都适用的
配置推导程序**。与证据相符 —— 同一程序在两个不同的池上给出各自正确的答案：

```
自采（位置 A 的池，含 rssi）   程序筛出 rssi → +0.2413（窗口级，9 任务）        ✅ 实测
UNSW（位置 B 的池，61 列）     程序应筛出该池中反转的族 → **未测**
                               而该池对同生态设备对的容量已实测有限
                               （二类 0.6504、最强单列强度 0.1168）
```

**代价一：不得再报「方法的准确率」这种池无关的单一数字。**性能是池依赖的；
每个数字必须同时标注**池**与**粒度**（后者见 §2.9）。

**代价二：外部验证从「锦上添花」变为「承重」。**「程序对任何池都适用」这一主张
必须在第二个池上检验 —— 即**在 UNSW 的 61 列上跑族级反转诊断，成为必做项而非可选项**
（该诊断在 UNSW 上**从未跑过**：`code/scripts/analysis/unsw_two_channel/check_unsw_families.py`
文件头自陈 "Produces no judgment-bearing numbers -- only column lists and group sizes"）。

**由此得到唯一池无关的评判指标：程序离它自己那个池的 oracle 有多远。**

```
自采（位置 A 的池）   ④ 流程终点 0.7604   ⑤ 同空间 oracle 0.7648   距离 0.0045
UNSW（位置 B 的池）   距离 **未测** ← 上述诊断应产出的数
```

该量衡量「给定手上有什么，程序有没有榨干」，而非「手上有多少」，故可跨数据集陈述：

> **在每一个池上，程序都逼近该池自身的最优；池的容量由方法自己报出
> （二类专用模型 + 逐列/族 AUC）。**

两句各有实测支撑：前半句自采 0.0045；后半句 `UNSW-BELKIN-CAPACITY` 的 0.6504 与 0.1168。
**但「程序对任何池都适用」目前 n=1** —— 距 oracle 0.0045 只在位置 A 的池上测过。

**重抽优先级（按可采性 × 实测强度）**：
1. **方向的更多刻画**（上下行包长比分布、上下行突发结构、间隔不对称）——
   两位置都可采，且实测最强：`UNSW-BELKIN-CAPACITY` 族内最强 `down` 0.1168 / `up` 0.1123，
   其余五族 ≤0.034；自采方向规则修复后困难簇强度同为 ≤0.10。
2. **802.11 帧头其它字段**（速率分布、重传率、`subtype` 细分、duration）——
   仅位置 A 可采；若择立场 A，这是最大的未开发池。
3. **时间结构**（自相关、周期性）—— 两位置都可采，但需更长观测窗。

**不抽**：IP/端口/DNS/TLS —— 仅位置 B 可采，且会离开加密友好定位、与 IoTDevID 正面竞争。

**扩池的前置条件**（见 §5 限制 6）：`HIER-CLASSPAIR` 已实测选择规则在 9 个接近候选间选错
（前四名相差 0.005，outer 上 Camera 代价 0.42）。**故必须先修选择规则，再扩池。**

## 1.2 抓包位置分类学，与「先扩交集」规则

**位置枚举（用户 2026-09-04 提出，据此定扩池方向）**：

| 位置 | 可采 | 不可采 | 我们的数据 |
|---|---|---|---|
| ① 空口（802.11 monitor） | 射频层：`rssi`、速率、重传、帧子类型、BSSID、MAC | IP 及以上（WPA2 加密） | **自采** |
| ② 网关/交换机镜像 | Ethernet + IP/TCP 头、端口、DNS、TLS 元数据 | 射频层 | **UNSW、CIC** |
| ③ **AP 自身** | **①∪②** —— AP 是无线端点（有逐 STA `rssi`/速率/重传）且持有密钥（可见 IP/DNS） | — | **无任何公开数据集** |
| ④ 设备自身 | — | 需设备配合，按 §1.1 排除 | — |
| ⑤ NAT 上游 | — | 设备身份被 NAT 抹掉 | — |
| ⑥ Zigbee/Z-Wave/BLE 嗅探 | 另一套射频与特征空间 | — | UNSW 非 IP 设备因此被排除 |

**故我们的两个数据集是同一位置（③）在两个方向上的投影**：
自采 = ③ 的空口投影（缺网络层）；UNSW/CIC = ③ 的网络层投影（缺射频层）。**两者互补，均非全貌。**

**特征因此分三块**：

```
交集      只需 (时间戳, 包长, 方向)      ①②③ 都可采   ← 方向在 ① 用 BSSID 判、在 ② 用设备 MAC 判
空口独有   rssi / 速率 / 重传 / 帧子类型   仅 ①③
网关独有   端口 / DNS / TLS               仅 ②③
```

**「先扩交集」规则（本规格采纳）**：扩池优先扩**交集**。理由不止实用 ——
**它是新特征能否被外部验证的唯一条件**：

```
扩交集       新族在自采上量出 → 可在 UNSW/CIC 上复现验证      ✅
扩空口独有    新族在自采上量出 → 永远无法外部验证              ❌ 重复 rssi 的坑
```

`rssi` 今日的困境（`UNSW-FAMILY-REVERSAL` 判定 `NO_REVERSING_FAMILY`：UNSW 池 7 族
`d_auc_sum` **全部为负、0 个正值**，故坐标 1 在该池自动不开火，干预效应量的外部复现
**在 UNSW 上已确定不可能**）正源于「效应量落在空口独有那一块」。
**再向空口独有方向扩，是把同一个坑挖第二遍。**

**运行前已确认现有 94/61 列的构成**（`code/scripts/core/robust_iot_research.py`
`summarize_window()` 为一个手写字典字面量，逐列硬编码，非选择所得）：

```
自采 94 = UNSW 61（交集）+ 33 列空口独有
          subtype 16 / rssi 8 / unique 2 / retry 1 / data,ctrl,mgmt 3 / null_data 1 / qos_data 1 / bssid_known 1
UNSW 61 中另有 2 列构造上恒零（`side_packet_ratio`、`other_packet_ratio` ——
          UNSW 提取器自陈「Ethernet 无管理/控制帧，按设备 MAC 归流后每包必为 up 或 down」）
          → **UNSW 有效池实为 59 列**；自采侧这两列亦近乎恒零
```

**现有 94 列完全未覆盖的（原料都在 pcap 里，只是提取器字典里没有这些键）**：
时间结构（自相关、周期性、FFT、间隔多峰性）、序列结构（包长转移模式、n-gram、方向串复杂度）、
方向的精细刻画（逐方向间隔分位点、请求-响应配对时延、上下行交替 run-length）、
跨窗结构（相邻窗口关系）。**前三类全在交集内**，故为扩池首选。

## 1.3 自采数据集的拓扑与负载（**声明的输入,不是本方法的结果**）

### 1.3.1 空口上只有 3 个发射机,却打了 5 个标签

| 标签 | 802.11 空口发射机 `wlan.ta` |
|---|---|
| `Camera` | `78:df:72:04:d6:b4`（自有电台） |
| `Socket` | `b8:50:d8:67:b5:d0`（自有电台） |
| `Light_T1` / `Light_XM` / `Sensor` | **同一个** `54:ef:44:59:eb:4c`（小米网关；三者是其后的 Zigbee/BLE 设备） |

**证据（2026-09-04 实测,数据集作者已确认）**：R2–R7 六轮全部如此；
`light_T1` 抓包文件里除 AP（`68:dd:b7:40:37:8a`）外没有第二个够量站点；
三者的 802.11 能力指纹逐字节相同（`wlan.tag.number` `0,1,50,45`、supported_rates、
HT caps `0x012c`、AMPDU `0x19`；Camera 为 `0x016e`/`0x1a`）；抓包单信道 2462 MHz。
落盘产物：`results/transmitter_partition_20260904/topology.json`（30 个 pcap 逐文件计数,
**「自有发射机恒为最大非 AP 站点」= True**）。

**`FILTER_EXPRESSIONS["raw_all"] = None`** —— 94 列缓存**无任何 MAC 过滤**,
标签仅由 pcap 文件名决定。三个网关文件因此含**跨标签污染**：
来自 Camera MAC 5437 帧 + Socket MAC 3279 帧 = **占网关帧 4.17%**。

**这是这个领域的公认结构事实,不是本数据集的毛病**：CIC IoT 2022 的官方 Readme
在 `4-Scenarios` 里自陈 *"These lamps use Zigbee. **Do NOT look for them in the dataset.**"*

### 1.3.2 措辞规定（强制）

**凡涉及 `Light_T1` / `Light_XM` / `Sensor` 的表述,一律写「一个网关的三条流」,
不得写「三台难分的设备」。** 它们不是难分,是**在空口上看不见**。
本文档此前多处「困难簇」一词,其所指即此三条流；保留该词作为**标签集合的简称**,
但不得据它推论"设备本身相似"。

### 1.3.3 负载是脚本施加的（合成,非自然使用）

采集时运行的是「10 s 开 / 10 s 关」的脚本(数据集作者 2026-09-04 确认)。
包级实测(按自有发射机 MAC 过滤、1 s 分箱、FFT)：**发射基频 10.06 s**,
谐波 5.03（/2）、3.36（/3）、2.52（/4）；各候选周期的功率占比 ——
**10.06 s 处 1.5%–18.8%**,而 15 s 处 0.11%–0.82%、20 s 处 0.06%–1.11%、30 s 处 0.03%–2.97%。
活跃 1 s 箱占比：sensor 0.22 / light_T1 0.25 / light_xm 0.32 / camera 0.37 / socket 0.51。

**三条后果**：

1. **窗长 10 s 已与物理周期对齐**（10.06 s ≈ 一个完整占空比）,**不得改窗长**。
   改成 30 s 会使窗数由 11303 掉到约 3768、削弱训练与设备级投票,
   并按 §2.9 丧失与全部冻结结果的可比性；且窗长与周期不成整数倍时会**人为造出周期假信号**。
2. **时间族与序列族无判别力是可预期的**：占空比由脚本施加、五个标签共有,
   故自相关 / FFT 主峰 / 间隔分布对所有标签一样。实测 `time` 族 `d_auc_sum` −0.0098、
   `seq` −0.5121、`dir` −0.5258。
3. **相位只区分出 Socket**：按 `window_id mod 3` 看,四个标签热在同一相位、
   只有 Socket 热在 phase0（69 vs 35/29）,而 Socket 本已恒为 1.0000。
   （跨标签相位对齐前提是各场抓包起点与脚本起点关系一致,此条有假设。）

**未解项,不编机制**：窗口级（10 s 网格）逐窗 `packet_count` 的自相关 lag3 稳定为正
（+0.25～+0.47）、FFT 主峰精确落在 3.00 个窗,而包级在 15 s 与 30 s 处几乎无功率 ——
**两者未能对上**。15 s 混叠假设已被 15 s 功率 0.11–0.82% 否掉。决策以包级为准。

### 1.3.4 会话身份与设备身份不可分离（上界警告）

每个 (设备, 轮次) 只有**一场**约 1 小时会话,故对那三条网关流,
「设备身份」与「会话身份」在数据内不可分离。两项缓解已实测：

- **日期已排除**：同日单元 `jit_R6`（05-26,三条流同日采集）上
  `F_gw` = 0.6820 ≫ 三类不可区分时的退化值 1/3 → **分离是设备信号,不是日期残留**
  （`TRANSMITTER-PARTITION-VALIDATE` 判据 B）；
- **时段已平衡**：三条流各自恰好 **3 场上午 / 3 场下午**,故时段不构成跨轮次仍存活的逐标签关联。

**未控项**：同日内小时仍不同（R6 为 17h / 16h / 14h）。彻底解开需会话交织式重采。
**故凡引用域内数字作为"可迁移余量"时,必须标明它是上界**：
网关三流域内 `F_gw` 0.8616（94 列）/ **0.8771**（183 列）,跨轮次 0.6784 →
落差 0.1832 **是上界,不是实数**。

## 2. 方法步骤（步骤 4 已否定，代之以步骤 4′）

### 参照点（不是步骤）

| 参照 | 含义 | 值 | 出处 |
|---|---|---:|---|
| `joint_tb` | **同环境、窗口级**参照：`H` 内联合训练（R2+R3+R4 的前 4 个时间块训练、第 5 块测试，`run_histint.py:45` `joint_eval`），**只用 `H` 的标签** | 0.9084（full94）/ 0.8694（drop_rssi） | `r567_94dim_retest_20260904/deltas.csv` |

**`joint_tb` 不是部署上限，两处易错须写明**：
① 它是**同环境**上限（"若完全没有环境变化，这套特征能到多少"），不是跨环境上限 ——
跨轮次实测 0.7604，与它相差 0.148，那个差是漂移的代价；
② 它是**窗口级**的，设备级数字可以超过它（流程在 R5/R6/R7 设备级 5 min 0.9776 > 0.9084），
**两者不可比**。它的唯一用途是量删族在同环境的代价（−0.0389）。

**关于"先联合训练拿到最高值再优化"的两种读法**：
`joint_tb` 是「联合 `H` 内的全部条件」，**不需要目标标签，属方法本体**；
若改为「联合训练包含新环境的数据」，则需要目标标签，属 §2.7 可选扩展，**不在方法本体**。
| 入口 `ⓠ` | 源域 CV 选配置（含 stacking 候选） | 0.5191 | `two_channel_20260903/eval_five_points.csv` |

### 步骤 1　族级反转诊断（只读 `H`）

族划分机械导出：`c.split("_")[0]`，规模 <2 的并入 `singletons`。
对 `H` 内的每个 LORO 任务、每个无序类对、每个族，计算剔除该族后的 ΔAUC，在全部类对上求和。
按该和降序排出候选（**只保留和为正的族**）。

**自动不开火**：若无任何族的和为正，候选集为空，不删任何族。
这是 `run_two_channel.py:321` `cand = [f for f, v in delta.items() if v > 0]` 的行为，**不是外加分支**。

实测（自采 `H`）：`rssi` 的 `d_auc_sum` = 5.2440，被排为第一并提议（`procedure_trace.json`）。
目标函数单位下重测排序一致（`HISTINT-OBJ-SIGNAL`：`S_obj` rssi 0.4140 vs 次名 singletons 0.0182，22.8×）。

### 步骤 2　验收与删除（只读 `H`）

按候选顺序逐个试删，在 `H` 的全部 LORO 任务上评估，接受第一个通过 `accept_family` 的族，然后停止。

实测：接受 `rssi`（8 列，94→86）。ⓠ 0.5191 → ③ 0.7544。

**负控（证明这不是普通特征选择）**：重要性 CV 选特征仅 0.5258（+0.0067，占 +0.2413 的 2.8%）。
机理：`rssi` 重要性 25.3% / `ΔLORO` **+0.2920**，`len` 重要性 22.0% / `ΔLORO` **−0.1610** ——
按重要性排序在原理上分不开这两族（`HISTINT-OBJ-SIGNAL`）。

### 步骤 3　在缩减集上定基模型与是否堆叠（只读 `H`）

以 `H` 内层 LORO 任务上的 `g = best_base − stacking` 均值为判据：`g > 0` 拒绝堆叠，否则允许。

实测（`PIPELINE-DROPRSSI-E2E`，判定 `SOURCE_SIGNAL_PARTIAL`）：

```
配置        inner g 均值   决策              outer 逐格一致
full94       +0.1697      REFUSE_STACKING    2/3（pos_R5 判错，代价 0.0244）
drop_rssi    +0.0043      REFUSE_STACKING    2/3（jit_R6 判错，代价 0.0039，在打平带内）
                                             合计 4/6 → PARTIAL
```

**已知可靠性上限**：规则在 6 格里对 4 格。判错的代价被实测的 `|g_out|` 界住 ——

### 步骤 4′　逐类对覆盖（**取代已否定的步骤 4,已双跑登记**）

步骤 4 的失败原因是**分层硬路由**：第一层路由一错,错误溢出到整个判决
（`jit_R6` 上 Camera 0.8131 → 0.4713）。步骤 4′ 换一个把错误**关在类对内**的结构。

**结构**：基座 = 完整池上的多类模型；对通过**三重闸门**的无序类对 `(i,j)`,
在该类对的掩码特征集上训一个二分类器；当基座输出的 **top-2 恰为 `{i,j}`** 时用它重判,
否则保持基座 `argmax`。**一次错误的覆盖只能在这两类之间挪概率,不能制造涉及第三类的新错误。**
（「有界」指错误的**种类**有界,不指数量小：`jit_R6` 上被覆盖的窗口是 1029/1816 = 57%。）

**三重闸门**（三条同时成立,形式与常量全部沿用已冻结实现）：

| # | 条件 | 来源 |

| ① | `accept_family` 三条件（`S_f>0`；`G/\|L\| ≥ 3.0`；最坏情况 `\|W\| ≤ 0.5×A`） | `run_two_channel.py:268` |
| ② | 类对内占优度 `S_f / max(S_次名, ε) ≥ 3.0`，`ε=0.05` | `UNSW-FAMILY-REVERSAL` §5 |
| ③ | 绝对下限 `S_f ≥ 0.15`（逐任务平均 ΔAUC ≥ 0.05） | 本步骤新增,取值理由见下 |

**③ 的取值与不敏感性（两条须一并陈述）**：该值在看过闸门数值分布之后选定。
观测分布是**两组、相隔 72 倍**：通过 ①② 的候选里 `rssi` 两格为 +0.9817 / +1.0601,
其余全 ≤0.0137,被拒者最大 0.0087 —— 故 **(0.0137, 0.9817) 内任何取值给出相同选择**。
**不是刀锋调参,但确实用了本数据的信息。**

**掩码只由 `|S|=2` 的三个 inner 任务导出 —— 这是硬要求,由实测强制**：

## 2.6 MAC 地址的三重角色，与「为什么不直接按 MAC 分类」

**MAC 在本方法中有三个互不相同的角色，必须分开陈述**：

| 角色 | 用在哪 | 是否进特征 |
|---|---|---|
| **真值来源** | 训练与评估的标签（`device_mac_map.csv` → `{mac → device_id}`；自采同理） | **否** |
| **端点分组键** | 步骤 5 的设备级累积按其分组 | **否**（`META_COLUMNS` 一律排除） |
| 特征 | **无** | — |

已逐项核实：`META_COLUMNS = {device, day, label, source_file, window_id, window_start,
window_end, window_start_epoch}` 一律不入特征；特征列中带地址字样的仅
`unique_sa_count` / `unique_da_count` / `bssid_known`，**全是计数或比例，不含身份**。

**「为什么不直接查 MAC 表」——四条，前两条是安全场景的核心**：

1. **MAC 是自声明的、无认证。**任何设备可宣称任意 MAC，故基于 MAC 的资产清点被一条命令击穿。
   而流量指纹要解决的正是这个场景：**不能相信设备自己说它是谁。**
2. **MAC 随机化。**iOS 14+/Android 10+/Windows 10+ 对 WiFi 默认随机化；IoT 设备目前多数不随机化，趋势明确。
3. **MAC 表只覆盖已知设备。**新接入的未登记设备查不到 —— 而这正是资产发现的主要用途。
4. **OUI ≠ 设备型号，我们自己的数据里就有反例**：`Dropcam` `30:8c:fb:2f:e4:b2` 与
   `NestDropcam` `30:8c:fb:b6:ea:45` **同一 OUI、两个不同产品**（亦即那对「设备表里有、
   流量里只有 209 窗」的存活者偏差案例）。

**正文该写的那句话**：不是「我们比 MAC 更准」（有 MAC 表时按 MAC 分类定义上就是 100%），
而是**「MAC 在被伪造、被随机化、或设备未登记时给不出答案，而流量形状仍然给得出」**。

### 2.6.1 分组键被破坏时方法会怎样（三部分，两部分已定）

**① 窗口级预测对 MAC 变化免疫 —— 由代码结构可证，无需实验。**
MAC 不在 `feature_columns` 中，故改动 MAC 值不可能改变任何特征值，因而不可能改变任何预测。

**② 分组键不稳定（随机化）—— 已测，即准确率-延迟曲线倒读。**
键每换一次，分组即断开；分组越短，每组窗口数越少，设备级退回窗口级：

```
键稳定 5 分钟   → N=30 → 0.9776
键稳定 1 分钟   → N=6  → 0.9161
键 10 秒即换    → N=1  → 0.7710
```

**③ 分组键被污染（两台设备共用一个 MAC）—— 今日实测（探索性，纯聚合冻结预测，
产物 `results/g0_environment_grid/grouping_key_margin_posthoc.csv`）。**
裕度用**无标签可算**的定义（`top1 份额 − top2 份额`）：

```
              裕度均值   裕度最小
full94  单设备  0.6282    0.1233
full94  合并对  0.1203    0.0151     塌 5.2 倍
strict59 单设备 0.5794    0.0025
strict59 合并对 0.1525    0.0126     塌 3.8 倍
```

**效应真实（均值塌 4–5 倍），但裕度不能当检测器 —— 区间重叠**：
`strict59` 单设备最小裕度 **0.0025**、合并对最大裕度 **0.3556**，
**不存在能分开「单设备」与「合并」的阈值**。

**故裕度的准确身份是「这一组不确定」，而不是「这一组被污染」** ——
困难设备 / 分组键污染 / 漂移三种原因它分不开。**作者跑前提出的「裕度同时是污染检测器」
这一说法据此否定。**

**且检测在分类器坏掉处结构性失效**（跑前写下的预期，已兑现）：
`full94` 下 `Light_T1+Light_XM` 合并后裕度 **0.434**（高于多数单设备），
因为这两台本来就都被判成 `Light_XM` —— 直方图未被劈开。

**方法不依赖分组键有语义**：它只需要「把包归到同一端点」的键，MAC 最方便但可替换
（关联会话、AP 的 STA 表项）。**分组 ≠ 识别**：分组不回答「是什么」，
且伪造者也须用一致地址收包，故分组在伪造下仍成立，而查表失效。

## 2.8 设计原则：不接受以牺牲高识别率设备换取总体提升

**总体识别率的提升必须来自「把低识别率设备拉到局部最优」，不得来自「牺牲已高的设备」。**
理由不是偏好，是可测的：macro-F1 是逐类 F1 的均值，因此一次交易在 macro 上可能为正而在逐类上有退化，
**只看 macro 看不见它**。

已测的对照（同一数据、同一诊断、只差干预的分辨率）：

```
族级（全局）删除 —— 必然是交易
  R567 逐类分解：八个单元 ΔCamera 全为负（−0.0239 ~ −0.3494），收益全部来自困难簇；
  Δmacro 恒等于五类 ΔF1 的均值（逐单元逐位核对）

类组级（局部）分解 —— 交易被打破（探索性单种子）
  逐类均值 Camera −0.0048 / Light_T1 +0.0222 / Light_XM +0.0236 / Sensor +0.0136 / Socket −0.0002
```

**结构性原因**：一个只有全局特征排序的干预**没有类对分辨率**，所以它只能全局加减，必然产生交易；
本方法的诊断量本就是逐类对的（`diag_coord1.csv` 逐 `(task, pair, family)` 记录），
因此干预可以局部化。**这不是「别人做不到检查逐类」——谁都能报逐类 F1；
是「全局排序的干预在原理上只能交易」。**这一点必须这样表述，否则会被一句话反驳。

该原则已写入 `PROTOCOL_HIER_CLASSPAIR_20260904.md` §6 的主判据：
条件 1（Camera/Socket 不退化，容差 0.01）**与**条件 2（困难簇三类均提升）须同时成立，
`HIER_TRADES` 分支专门用来接住「又是一次交易」的情形。

## 2.9 报数硬规矩：粒度必须成对报，且不得跨粒度比较

**逐窗口与设备级是两个不同的任务，不是同一任务的两个成绩。**

```
任务                                     IID（同轮次）      跨轮次 R5/R6/R7
逐窗口：给这 10 s 窗口贴标签               0.8896 – 0.9281    0.7710
设备级：给这台设备贴标签（N=30 窗投票）     1.0000             0.9776
```

**判决数差 30 倍**：逐窗口每单元约 1800 个判决；设备级每设备仅 12–13 个块
（每设备每单元 363–406 窗，`pipeline_droprssi_20260904/device_margin.csv`），
一个单元约 60 个判决。**12 个块的分辨率下，错一个块该类 F1 即掉约 0.08，
故设备级看不见比 8% 更细的差别。**

**「设备级 1.000」的准确含义**：N=30 投票 ≈ 读该设备预测直方图的 argmax
（180 格中仅 1 格不一致，`aggregation_audit_devices_posthoc.csv`），
所以它等于「每台设备的窗口里占多数的那个类是对的」——
在逐窗口 89–93% 时这是自动成立的，**不等于「完美识别设备」**。

**三条硬规矩**：
1. 任何识别率数字必须标明粒度（10 s / 1 min / 5 min），且**成对报**；
2. **禁止跨粒度比较**。本文档 §2 曾把设备级 0.9776 与窗口级 `joint_tb` 0.9084 相比并称
   「越过天花板」——**该比较无效，已订正**；
3. 「方法有多好」看**逐窗口**（分辨率高 30 倍，且剩余空间 0.098 全在这一侧）；
   「部署能不能用」看**设备级**。头条数字用逐窗口，不用设备级。

**每个「上限 / 最优 / 唯一 / 必然 / 接近 1」这类强词，必须同时标明它在哪个粒度、
哪个口径、哪个规模下成立。**今日已有五处因缺此标注而措辞过强并订正
（`+0.42` 口径、「同推翻率」分母、「相关→独立」机制、方向修复归因、`joint_tb` 上限）。

## 2.10 任务分层报数规则（由 §1.3 的拓扑强制）

**自采上的「5 标签识别」不是一个任务,是两个,必须分开报**：

| 层 | 内容 | 窗口级实测 | 占全部错误 |
|---|---|---:|---:|
| (i) **3 发射机分类** | Camera / 网关 / Socket | **0.9724**（Camera 0.900、网关 0.9873、Socket 1.000） | 13.5% |
| (ii) **网关后三流的活动推断** | `Light_T1` / `Light_XM` / `Sensor` | 三流内部 0.7005 | **86.5%** |
| 合计（5 标签） | — | 0.7952 | — |

**两者之差 0.1772 全部来自 (ii)。** 层 (i) 在窗口级已基本解决,而且 10 s 即达、不靠聚合。

**三条规矩**：

1. **不得只报 5 标签的总数字**而不分层 —— 那会把一个已解决的任务和一个开放问题混在一起；
2. **层 (ii) 是本工作的主要难点,也是公开数据集在结构上无法提出的问题**
   （UNSW 每标签一个 MAC；CIC 官方声明 Zigbee 设备不出现在抓包里）；
3. 论文若引层 (i) 的数字,须同时声明三条流被合并；若引 5 标签数字,须同时声明 §1.3 的拓扑。

**写作时的准确措辞**（可直接使用）：

> 我们在一个**网关中介**的部署中采集数据:五台目标设备中三台经同一个网关接入 WiFi,
> 因此在 802.11 空口上仅表现为**三个发射机** —— 该拓扑在真实家庭 IoT 部署中是常态,
> 而现有公开数据集均为每设备独占一个 WiFi 端点的网关侧抓包,无法呈现该情形。
> 相应地,本文任务分两层:(i) 三发射机的分类,(ii) 网关后三台非 IP 设备的活动推断。
> **拓扑真实,负载合成**（§1.3.3）。

## 3. 输出

1. 配好的分类器（特征集 + 基模型 + 是否堆叠 + 是否类组分解）；
2. 逐设备判决 + 众数裕度（无标签置信）；
3. 决策轨迹：每一步选了什么、依据的 `H` 内数值是多少（可审计）；
4. 不开火记录：若候选集为空 / 无困难簇，明确记「未干预」。

## 4. 「算不算方法」的可判定门槛

> **同一份未修改的代码，在自采 `H` 上产出「删掉 rssi 族」，在 UNSW `H` 上产出「不删任何族」，
> 两边分别给出 0.9776（R5/R6/R7 设备级 5 min）与 0.999（UNSW 易类设备级）。**

- 跑得出来 → 「每个环境现场推导」从设计属性变成两个环境上的实测事实。
- 需要手改任何一处 → 手改处即方法的洞。**此前已知的那一处（步骤 4 簇成员写死）已消除**：
  `HIER-CLASSPAIR` §3 实测由源域 τ=0.1 聚类程序性导出 `{Light_T1, Light_XM, Sensor}`，
  跨三模型、跨五种子一致。**当前无已知手改点** —— 步骤 4′ 的三重闸门亦为程序化
  （不指定任何族,由 ①②③ 自行选出；在 94 列与 183 列两个池上给出同样的选择）。
  **但第 5 条（同一份代码跑 UNSW）仍未检验；且闸门 ③ 的取值用了本数据的信息（步骤 4′）。**

## 5. 已知限制（写在前面，不让读者自己发现）

1. **不抬天花板。**方法配置既有特征集，不产生新信息。UNSW Belkin 对配得再好也是 0.6504 ——
   61 列里最强单列强度仅 0.1168（`UNSW-BELKIN-CAPACITY`）。
2. **概念不新。**「按跨环境不变性选特征」已有 ICP / IRM / stable learning；
   本方法独有的是逐类对**带符号**的诊断、把损伤定位到集成元层跨类映射的因果消融
   （`meta_soft_cls`：只拿掉跨类项恢复 96.7%）、以及现成域适应工具在本数据上**实测有害**
   （CORAL/SA `DA_DOES_NOT_HELP` −0.0365 / −0.0893）。**参考文献须核实后再引。**
3. **干预的效应量只在一个测试床上测到。**`rssi` 在 UNSW/CIC 结构性缺席（网关侧有线抓包）。
   **【2026-09-04 订正:族级诊断已在 UNSW 上跑过】**`UNSW-FAMILY-REVERSAL`（双跑一致）：
   7 族 `d_auc_sum` **全部为负、正值族 0/7** → 该池无反转族,坐标 1 **自动不开火**
   （`cand` 为空是冻结代码行为,非外加分支）。故「干预效应量的外部复现在 UNSW 上已确定不可能」
   —— 不是没找到,是测出该池无可供干预的病理。**A 层（诊断形式与程序特异性）由 n=1 变为 n=2；
   B 层（干预效应量外部复现）关闭。**
4. **步骤 3 的规则可靠性 4/6。**
5. **规模**：5 台设备、一个房间、六轮次。
6. **候选接近时的选择行为已测，且失败。**步骤 1 只面对过一次压倒性赢家
   （**336×**；此前本文档与 `UNSW-FAMILY-REVERSAL` 判定书写作「22.8×」,
   那取的是 `HISTINT-OBJ-SIGNAL` 的 `S_obj` 口径,与 `d_auc_sum` 不是同一个量,
   同口径应为 5.2440/0.0156 = 336×,已订正；判定不受影响）；
   而 `HIER-CLASSPAIR` §4 在 9 个候选（前四名相差 0.005）间选择时选错，
   outer 上 Camera 代价 0.42。**故任何扩大候选池的动作，必须先修选择规则** ——
   否则候选越多，「inner 分不出、outer 差很多」越会成为常态而非例外。
7. **方法不搜索特征，只在给定特征集内自优化。**搜索空间 = {删哪些族} × {基模型} ×
   {堆不堆叠}；**不含「从原始流量算哪些特征」**。故诊断量对未被抽出的特征是盲的，
   且可能删掉「现有集合里最好的族」仅因更好的那个没被抽出。
   扩池是方法身份（候选验收程序）的另一半，但受限制第 6 条约束。
8. **`H` 增长时边际价值递减**（见 §2.7）。
9. **方法只会删,没有任何机制去*发现*一个特征的正向作用。**动作空间是
   `{删哪些族}`（步骤 4′ 后细化为 `{对哪些类对删哪些族}`）,不含正向选择或变换。
   **实测证据**：`FEATURE-EXPANSION-SELF` 的并报量 `Δ(N89−N33)` = **+0.0065 > 0**,
   即作者按证据筛选出的 33 列靶单**丢了信息**,被判为无用的那 56 列在帮忙。
   故「有些特征的作用尚未被发现」按构造成立。
10. **「用源域证据挑模型容量」这条路已测,且关闭。**10 个配置 × 3 种子,
    inner（`|S|=2` 三任务）与 outer 排序 **Spearman ρ = −0.1030（p = 0.7770）**；
    outer 最优容量 **regime 依赖**（`jit_R6`→`xgboost`、`jit_R7`→`rf`、`pos_R5`→`rf`）；
    outer 最好与最差仅差 **0.0254**,默认 `xgboost` 距容量 oracle 仅 **+0.0056**。
    （后悔值恰为 0.0000 系 inner/outer 的 argmax 偶然同为 `rf`,在 ρ=−0.10 下不构成证据。）
    **超参一次未搜过,且不搜** —— `build_model` 的值逐字沿用。
11. **在域内测出的特征集价值,系统性低估其跨域价值。**同一批 89 列新特征：
    域内天花板 `joint_tb` 增益 **+0.0134**（`FEATURE-EXPANSION-SELF` 的主判据,
    据此判 `EXPANSION_MARGINAL`）vs 跨轮次窗口 macro 增益 **+0.0355**（27/27 为正）,
    **比值 2.6×**。**该判定本身不改**（由 `Δceiling` 单独定义、双跑一致）,**含义更正如上**。
    推论：**评估新特征不该只看域内天花板。**
12. **域内数字含会话身份泄漏**（§1.3.4）。凡引用「可迁移余量」须标明是上界。
