## 一、Context：为什么要改 v1

v1 把第一批工作定为"零成本实验 → 方法章"。核对代码与既有产物后发现三个问题，都位于方法章之前，且都会污染方法章。

### 问题 1：项目里有三个不同的 CPD，互相矛盾

| 任务 | CPD-A<br>`cpd_comprehensive_analysis.py`<br>（基准 = 三个 IID CM） | CPD-B<br>`controlled_cpd_experiment_v2.py`<br>（基准 = 六环境 pairwise） | CPD-C<br>`controlled_cpd_experiment.py`<br>（基准 = joint CM） |
|---|---:|---:|---:|
| **loro_R2_R4_to_R3** | **0.8397（最高）** | **0.1521（Low）** | **0.801（High）** |
| loro_R2_R3_to_R4 | 0.8905 | 0.1254（Low） | 0.836 |
| loro_R3_R4_to_R2 | 0.3489 | 0.1623（Low） | 0.317 |
| position_R5 | 0.5670 | 0.5670 | 0.533 |
| jitter_R6 | 0.4109 | 0.4109 | 0.356 |

根因在 [six_env_confusion_similarity.py](../code/scripts/analysis/six_env_confusion_similarity.py) 第 33-39 行的 `env_mapping`：R2/R3/R4 指向 `single_round_*`（IID 模型），R5/R6/R7 指向 `position_*`/`jitter_*`（在 R2+R3+R4 上训练的 OOD 模型）。因此那个 6×6 矩阵**不是同质的"环境×环境"对象**——左上块是 IID-vs-IID，右侧块是 IID-vs-OOD。

这解释了两件事：为什么 position/jitter 在 A 与 B 下数值完全相同（到小数点后四位）；以及为什么 LORO 行差 5.5 倍——对 LORO 任务，CPD-B 从未读取 LORO 模型的混淆矩阵，它比较的是两个 **IID** 拓扑之间的差异。

**直接后果**：被 [README](../README.md) 与 [CPD_FINDINGS.md](CPD_FINDINGS.md) 指为权威机制验证的
[CONTROLLED_CPD_MECHANISM_VALIDATION_FINAL.md](../results/robust_v2/report/CONTROLLED_CPD_MECHANISM_VALIDATION_FINAL.md)（用 CPD-C）把 `loro_R2_R4→R3` 判为 **High**，并声称 Low→Medium→High 单调；而更晚的 v2 脚本（用 CPD-B）把同一任务判为 **Low**。用 v2 的 `controlled_cpd_data_v2.csv` 重算三桶均值是 Low −0.0171 / Medium −0.0008 / High −0.0194，**单调性不成立**。v2 没有配套报告，两套结论从未对账。

### 问题 2：载荷统计量 r=−0.630 由单点支撑

v1 第六节把论证重心放在 r=−0.630 上。但 n=11 中只有 `loro_R2_R4→R3` 的 gain 是 −0.0693，其余 10 个全在 −0.033 到 −0.0001 之间。手算留一后 r 从 −0.630 掉到约 **−0.36（p≈0.3）**。报告自身第 6.1 节也承认最高 CPD 的 `loro_R2_R3→R4` gain 只有 −0.0028、是"异常点"。原始的 Spearman p=0.1173、permutation p=0.0630 本来都不显著。

### 问题 3：证据只覆盖"环境组合"一个轴

即使把任务数提上去，也必须说清边界：所有任务都是同 5 台设备、同一房间、6 次采集的重组，任务之间高度相关，**有效样本量远小于任务数**。设备数与测试床数这两个轴完全没有改善。

更技术性的一点：K=5 时行归一化混淆矩阵的离对角只有 20 个自由项，而 Socket 恒定完美（110 条结果中 96 条 F1=1.0）→ 实际只有 4 类有效 → **CPD 实质上是对 12 个数取 Frobenius 范数**。在 16 类数据集上这个数是 240。引入第二个数据集不只是样本更多，而是让这个度量第一次拥有足够的拓扑维度，对度量可信度是质变。

### 结论与预期产出

瓶颈不是种子数、不是 Socket 泄漏、也不是方法章排期，而是**核心定量结论站在 n=11 和一个杠杆点上，且口径依赖**。

v2 做两件事：把证据基座从 11 个手工任务换成约 150 个枚举出的环境组合（纯 CPU、复用现有特征缓存、无需新采集），并冻结单一 CPD 实现。这同时解决 n 问题、口径矛盾、六环境矩阵不同质、路线 A 缺标定集、留一脆弱五件事，且全部在夜间算力上完成。

同时把公开数据集验证从"审稿修改轮"提前到投稿前（见 P7）。全文押注 CPD 是**普适机制**，检验这个押注最快的办法就是第二个数据集；若复现不了，framing 要从"机制论文"改为"案例研究 + 方法"，这必须在 11 月动笔前知道。

   - `normalize_cm(cm)` — 行归一化，沿用现有口径（`cpd_comprehensive_analysis.py:88-92`）

## P4 · 多种子深度重跑（W1 挂后台，GPU）

四个深度模型现在全是单种子 42。TDR-CNN 相对 MSR-CNN 的差距是 IID −0.0013 / OOD +0.016 / CPD −0.032，单种子无法排除随机性——而它正是"表达能力 ≠ 拓扑鲁棒性"这条论点的关键证据。

- 入口用 [cnn_contrast_search_experiment.py](../code/scripts/analysis/cnn_contrast_search_experiment.py)，它通过 `--split-source results/robustness_scaling_20260706_v2/splits` **复制**固定划分（第 60-65、252 行），所以改种子不会改划分

**验证**：若 TDR-CNN 与 MSR-CNN 的 OOD 差距小于 1 个 std，该论点在正文降级为"趋势性观察"，改以 CPD 差异为主证据。这个退路现在就要准备好，不要等 11 月。

## P5 · 方法章（W3-W7，硬死线 10/15）

路线 A/B 的技术内容沿用 v1 第五节，改两处判据。

**Go/No-Go 判据换成选择遗憾，不用相关系数**（n 小时相关系数置信区间宽到无法决策，且 P0 已证明它口径依赖）：

```
标定：在 P1 网格上按 leave-one-environment-out 标定阈值
测试：在留出环境上评估
通过条件（两者同时满足）：
  1. 平均 selection regret ≤ 0.01
     regret = F1(事后最优模型) − F1(代理指标选出的模型)
  2. 存在至少一个环境，选择器选了 Stacking 且该选择正确
否则 → 转路线 B
```

第 2 条用于避开退化解。v1 的"及格线：至少打平 RF"有个陷阱：选择器只要永远选 RF 就自动达标，审稿人会判定方法等价于"别用 Stacking"，一句话否掉整章。因此**必须同时报**：对 oracle 的 gap，以及对"永远 Stacking"和"永远 RF"两个固定策略的逐环境 win/loss 表。

**一个必须正视的负面信号**：repo 里唯一现成的无标签环境级代理（CPD-B / `cpd_env`）在旗舰案例上给出 0.1521（Low），而该任务恰是最严重的集成崩溃（gain −0.0693）。也就是说**现有 a-priori 代理在最关键的点上失效**。路线 A 的第一个问题不是"代理相关性够不够高"，而是"能否构造出在这个点上不失效的无标签代理"。P1 网格的 150 个点是回答它的必要条件。这个风险要在 9 月初导师会上讲清楚，不要留到 10 月。

## P7 · 公开数据集：CPD 普适性检验

**定位**：不是"扩大分析"，而是**对论文中心押注的一次廉价可证伪检验**。只做两个检验。

### P7a 数据集与特征提取器（W2，约 3 天）

**选数据集的硬标准**

| 标准 | 原因 |
|---|---|
| 同一批设备有 ≥3 个可分离的"环境"（会话 / 天 / 位置 / 重复） | CPD 定义在环境之间，不满足则无法做 |
| 设备类别数 ≥ 10，越多越好 | 混淆拓扑自由度 = K(K−1)；K=5 只有 20 项且 Socket 退化，是当前最大的度量硬伤 |
| 每个 (设备, 环境) 有足够窗口估出稳定的混淆矩阵 | 否则 CPD 是噪声 |
| 稳态运行流量优先于配网阶段流量 | 与本文场景一致；配网流量的"环境"更像协议阶段而非环境漂移 |

#### 选定：UNSW / Sivanathan IoT traces（IEEE TMC 2018）

https://iotanalytics.unsw.edu.au/iottraces.html — 2026-08-25 已直连核实，四条硬标准全部满足。v1 的调研未覆盖此数据集。

| 项 | 核实结果 |
|---|---|
| 环境轴 | **20 个连续逐日采集，2016-09-23 → 2016-10-12，无间断** → 天然的"跨时间轮次"，对应本文的 LORO |
| 类别数 | 设备清单 23 个 IoT MAC；抽样日 `16-09-30` 有流量 20 台，**≥100 个 10s 窗口的 16 台** → 可用 16 类 |
| 混淆拓扑维度 | 16 类 → 离对角 240 项（自采数据有效仅 12 项，**20 倍**） |
| 可混淆分组 | 含 **5 台摄像头**（Dropcam / TP-Link Day Night / Samsung SmartCam / Insteon / Netatmo Welcome）、3 台插座开关、多个传感器 → 天然近似类簇，正是 CPD 要刻画的结构 |
| 流量类型 | **稳态运行**，与本文场景一致 |
| 体积 | pcap 20 天合计 **9.5 GB**（单日 101 MB – 3.9 GB）；本机 `/home` 剩余 1.6 T |
| 许可 | MIT-0 |
| 标注 | 网关抓包，Ethernet 帧；按 `eth.src`/`eth.dst` 查 MAC 即可精确标注（网关 MAC `14:cc:20:51:33:ea`），无需推断 |
| **必须用 pcap，不能用 CSV** | 官方 CSV 仅 4-17 MB/天，但 **`TIME` 是 int64 秒级时间戳**（实测单日 673,415 包只有 84,291 个唯一时间戳）→ `interarrival_*`、`burst_*`、`subwin_*` 三族特征全部失效 |
| 工具链 | 本机 `tshark 3.2.3` 已装 |

**实施要点**

- 环境组合不要照搬 150 网格：20 天的子集枚举量太大。改用"连续 k 天训练 → 之后某天测试"（k ∈ {1,2,3}），覆盖近距离与远距离天对，控制在 100 个任务量级
- 类别极不均衡（Dropcam 约 7940 窗口 vs PIX-STAR 约 64）→ 复用 `robust_iot_research.py` 的 `sample_balanced`
- 丢弃流量过少的设备（NEST Protect 约 4 窗口、Withings scale 约 3、Blipcare / Nest Dropcam 当日为 0），并在正文写明入选门槛

#### 次选：IoT Sentinel（Aalto，Marchal）

https://research.aalto.fi/en/datasets/iot-devices-captures — 官方描述核实：31 台设备 / 27 类（4 类各 2 台），每类 ≥20 次重复，文件名 `Setup-X-Y-STA.pcap`，**X 是执行安装的人**。

v1 把它列为主候选，**核查后建议降为次选**：它是**配网/安装阶段流量**，不是稳态运行；"20 次重复"是重复同一套安装协议序列，差异来自操作人和序号，**不构成受控的环境漂移**。重复采集更接近 i.i.d. 抽样而非不同环境，LORO 类比站不住。类别数 27 是它唯一优势。可作为"操作人作为漂移轴"的补充实验留在附录，不作主验证。

**已排除**：YourThings（安全评分站点，非多环境流量集）。

#### 特征提取器

现有 extractor 是 802.11 专用的（`wlan.fc.type`、`subtype_*_ratio`、`retry_ratio`、`rssi_*`、`bssid_known`、`unique_sa/da`）。UNSW 是 Ethernet 抓包，这些不可用。但 94 维里约 60 维是通用的（`len_*`、`interarrival_*`、`burst_*`、`subwin_*`、`up/down_*`），所以这是**给现有 extractor 换一个链路层分支**，不是从零写。

**关键认识：特征不必对齐，不对齐反而更强。** 若 CPD 在一套完全不同的特征、不同链路层、16 个类别上依然出现，就排除了"CPD 是那 94 个 802.11 特征的产物"这一质疑。这一点要写进正文。

### P7b 两个检验（W8-W10，与 P6 并行）

1. **CPD 存在性**：在 UNSW 的天级环境上跑同样 5 个模型 + LORO 式划分，检验 (a) OOD CPD 是否显著高于 IID CPD；(b) 高 CPD 划分下 stacking gain 是否转负。这是机制主张本身
2. **路线 A 零重标定迁移**：把在自采数据上标定好的选择器**不重新标定**直接用到 UNSW，报 selection regret。若成立，这是二区论文里很强的结果——一个在 5 台设备单实验室标定的阈值迁移到了另一个数据集

**决策规则（预先写死）**

```
检验 1 通过 → 正文保持"机制论文"framing，公开数据集进正文（一图一表）
检验 1 不通过 → framing 改为"单测试床案例研究 + 方法"，
                公开数据集结果如实进讨论章，作为负面证据与边界条件
检验 2 通过 → 作为方法章的迁移性证据，进正文
检验 2 不通过 → 进附录，正文限定方法适用范围为"同部署内标定"
```

**不做**：跨数据集完整基线对比、公开数据集上的深度模型、特征工程调优。留给审稿修改轮。

## 八、风险

- **网格结果可能削弱结论**：150 个点上 CPD 与 gain 的关系可能比 n=11 弱。这是好事而非坏事——现在发现还能调整叙事（转向机制的定性证据 + 方法章的实用价值），11 月发现就来不及了。P0 的留一分析已预示这个方向，要提前接受
- **网格不解决设备/测试床轴**：150 个任务高度相关，有效样本量远小于 150。正文限制章节必须写明，缓解手段是 P7。不要在正文里把 150 说成 150 个独立样本
- **公开数据集可能复现不了 CPD**：这正是提前做的原因。P7b 的预注册决策规则保证无论结果如何都有写法，但要接受 framing 可能从"机制论文"降为"案例研究 + 方法"
- **P7 数据集风险已解除**：v1 的调研结论是"无数据集同时满足空口+链路层+多轮漂移+稳态运行"，但 UNSW 满足四条硬标准（20 天连续稳态 / 16 可用类 / 每类窗口充足 / MIT-0），9.5 GB 本机可容，tshark 已装。剩余风险转为工程量：需给 extractor 写 Ethernet 分支，且 802.11 专属特征在该数据集上不存在——这不影响 CPD 与路线 A，二者作用在预测层
- **路线 A 可能不成立**：现有 a-priori 代理在旗舰案例上失效是明确的负面信号。10/15 硬死线要真的执行，路线 B 是工程活、风险可控
- **导师沟通**：审计结论会推翻一份已被 README 引用的报告。9 月初的会上建议作为"发现并修正了口径问题"来讲，这比带着矛盾数据写完论文强得多
